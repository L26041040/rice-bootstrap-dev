3. 為什麼 Stop 比其他方案可靠
════════════════════════════════════════════

vs **PostToolUse(Write|Edit)**（權威文件推薦的通用答案，但這裡不適用）：
  - 致命點：PostToolUse 的 matcher 比對的是**工具名稱**。Matt 的 skill 是
    prompt-driven，寫檔可能走 Write / Edit / MultiEdit，也可能走
    Bash heredoc；只要它用了 matcher 沒列到的工具，這個 hook 就整個錯過。
    Stop 不在乎檔案「怎麼」出現的，只在乎回合結束時狀態如何——對一個
    我們無權改寫、且明說自己非決定性的外部 skill，這是決定性的可靠度差距。
  - 次要點：PostToolUse 會在 Matt skill **還在跑的中途**就把訊息塞回 model，
    可能打斷 Matt 自己的 step 3（給草稿讓 OWNER 編輯）與 step 5（自己回報
    完成）。等回合結束再續接，才真正符合「不 fork / 模擬 / 改寫 Matt skill」。
  - 成本：PostToolUse 每次寫檔都 spawn 一次 process；Stop 每回合一次，
    數量級更低。兩者的第一道 guard 都只是一次 stat()，marker 不在時極廉價。

vs **UserPromptSubmit**：要等 OWNER 再打一次字才會續接，等於把「再互動一次」
  換個形式塞回來，不符合 invariant 的精神。

vs **SessionStart / SessionEnd**：都要跨 session 邊界才觸發，等於強迫 OWNER
  開新 session，直接違反 invariant。

vs **FileChanged**（文件列出的事件之一）：語意上是最貼的（「檔案變了」），
  可能比 Stop 更小更準，但它被歸在 Configuration 群組，是否涵蓋任意 repo
  檔案未經證實——列為「值得花十分鐘實測，若成立可取代 Stop」的候選，不建議
  在未證實前押上去。

Stop 的已知限制與對應：
  - OWNER 中途 Ctrl+C 中斷該回合 → Stop 不觸發。下一個正常結束的回合會補上，
    自癒，不需額外機制。
  - 連續 block 8 次以上會被 Claude Code 強制忽略 → 我們的設計天生不會連續
    block：PASS 之後 marker 被 verifier 刪掉就永久靜默；FAIL 時用文件明載的
    stop_hook_active 訊號只出聲一次。
  - Stop 的 exit 2 + stderr 是**送回 model**，不是直接顯示給使用者——這正好
    是我們要的（要 model 接手 commit & push 並回報），但這一點必須實測確認
    （見第 6 點）。

# B. Verify 的責任

`verify.py` 是唯一最終檢查哨與 PASS/FAIL authority。
